# mod-procedural-dungeon

Procedurally generated dungeons: per-run unique layouts assembled at runtime
from existing WMO/M2 GameObjects on a client-known base map (default 37).
No client patch. See [README.md](./README.md) for install/usage and
`share-public/docs/World of Warcraft/procedural-dungeon/` for the full design
doc.

Engine-free like the rest of `src/generator/`. Rooms are single blocks (66.67 yd). **Since Round B (2026-09-02) the layout is a chain**: one path from the entrance through the boss rooms (boss *k* at `round(k·(L−1)/N)`), one-room pockets hanging off ordinary spine rooms, then the Phase-2 chest stubs; `chainIndex` / `branchOf` / `detourOf` on `PlacedBlock` are what B1/B3/B4 read (`detourOf` marks a **loop room**: since B0b an extra room beside a straight corridor run of the spine, entered from the run and left back into it two cells on — `V2.DetourChance`, 33 % per boss segment, additional to the room count). | `src/generator/PDv2GameMath.h` | **PDv2 gameplay math**: the 01 §8 formulas (rooms/boss counts, caster ratio, mob level band, loot multiplier, the dxp curve) plus the difficulty dial. Header-only and engine-free, so the harness pins every player-visible number. | `src/generator/PDv2WalkGrid.*` + `PDv2WorldMath.h` | **PDv2 walkable surface**: walk grid built from the kit's masks, A*, path simplification, the `PlanApproach` chase policy the creature AI runs on, and the world↔block/cell math in both directions (map 760 has no mmaps — this grid IS the navigation). Since **Round C / C1** `GridLineWalkable` is a true **supercover** test — an exact integer DDA over every cell the segment between the two cell centres enters, plus the **no-corner-cutting rule**: where the segment passes exactly through a cell corner, BOTH straddling cells must be walkable, because a creature has a body. Round B's Bresenham sampler skipped one cell at every minor-axis transition, which is how the patroller walked through walls; 2 136 of the 301 084 legacy-approved intra-mask pairs (0.71 %) really did cross a wall cell's interior, and the corner rule removes a further 7 468. Pinned in the harness twice: `PD_SUPERCOVER_PAIRS_PIN` over every kit mask, and `CheckCornerRule`'s **eleven** hand-built cases, which are the only in-tree oracle for the corner half - three of them walk the same 45 degree corner BACKWARDS, because the rule reads `At(x + sx, y)` / `At(x, y + sy)` and every positive-delta case leaves the sign untested |
| `src/generator/PDv2SpawnAnchors.h` | **PDv2 typed kit anchors** (Round B / B1). Header-only, engine-free decoder for the per-chunk `anchors` JSON that script 48 writes into `pdungeon_chunk_meta`: `entry`, `boss`, `chest` and the role-tagged `spawns` (`melee`/`caster`/`elite`/`patrol`). `PDv2DecorPlan`'s `DecodeAnchorList` flattens the same JSON into one clearance list and throws the KIND away; this decoder keeps it, and the kind is what the spawn veto's fallback (entry), the loop-room chest (chest) and B2's spawn placement (boss, spawns) read — B1's altar read `entry` as well, until Round C / C5 deleted it. The number reader is hand-rolled on purpose: `std::strtod`'s decimal point follows the C locale, so a comma-decimal worldserver would read the entry anchor's `29.166666` as `29`. Since **B2** the file also carries the placement itself: `PlanSpawnPoints(anchors, bossRoom, roles)` answers, for one room's picks, WHERE each stands — pick 0 of a boss room on the `boss` anchor (the arena centre), every other pick on the first unused anchor whose role matches (`elite` matches anything), then on any unused anchor, then on the legacy 12 yd overflow ring around the block centre. Pure geometry in a `PDv2SpawnPoint` (the plain names `SpawnPoint` and `PlannedSpawn` are both taken by the v1 generator): no draw, no engine include, so it can never move a layout and the harness can pin it chunk by chunk. Harness rules: every room chunk publishes an entry anchor on a walkable cell, every multi-socket corridor ≥ 2 `patrol` anchors, every dead-end stub a chest, and every planned point of every room-role chunk lands on a walkable cell |
| `src/generator/PDv2AmbushPlan.*` | **PDv2 ambush plan** (Round B / B5). Engine-free: per boss segment `Chance(V2.Ambush.Chance)` — always drawn, so a segment's coin is never skipped for want of geometry; the pick after it draws only where a segment offers two or more candidates, which is the one place the geometry reaches the stream — and on a hit one corridor of that segment's spine runs (`SpineRunInto`, so never a chest stub or a loop strip) is drawn with `UniformInt`. Runs on its OWN stream, `layoutSeed ^ PD_AMBUSH_SEED_MIX`, like the decor and critter draws, so turning the chance can never move a layout an account already owns. The chance is an operator key read live from the `.conf`, never a layout input. The harness pins the plan twice — `PD_AMBUSH_PLAN_PIN` (seed 12345 at chance 100, so it states WHERE the spots land) and `PD_AMBUSH_PLAN_PIN_MID` (seed 12345, four rooms, four bosses, at chance 50: the only check in the file that runs where `Chance` draws at all) — and re-derives the candidate corridors with its own walk |

## Core touchpoints (no core edits)

- `AllMapScript::OnBeforeCreateInstanceScript` → attaches `PDInstanceScript`
- `Map::SummonGameObject/SummonCreature` → batched build-out in `Update()`
- Per-instance dynamic collision tree → LoS (`CheckGameObjectLoS = 1`) + height
- `GameObject::SetGoState` → gate open/close (boss gate logic)

## Conventions

- Reserved IDs: GO 910000–910099, NPC 910500–910549 (registered in
  share-public `06-custom-ids.md`)
- Determinism: never use std `<random>` distributions in `src/generator/`
  (implementation-defined) — only `PDRandom` helpers; keep iteration orders
  fixed. Same seed must yield the same dungeon on gcc/clang/MSVC.
- Both harnesses must stay green: `pdgen --batch 500` and `pdblock --batch 500`
  = 0 failures.
- The block planner's manifest is a **contract with two other implementations**:
  `scripts/49_pd_compose_blocks.py` in the ForgottenLand2.0 workspace (the
  byte-exact oracle for the client composer) and the `FLPD2` parser in
  `fl-stream-client`. After changing `EmitManifest`, feed a real manifest
  through the oracle — `pdblock --manifest <seed> <file>` then
  `python 49_pd_compose_blocks.py --manifest <file>` — or the three will drift.
- AC code style, `-Werror`-clean; run `apps/codestyle/codestyle-cpp.py` from
  the module root before committing.
