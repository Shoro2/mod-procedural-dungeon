# mod-procedural-dungeon

Procedurally generated dungeons: per-run unique layouts assembled at runtime
from existing WMO/M2 GameObjects on a client-known base map (default 37).
No client patch. See [README.md](./README.md) for install/usage and
`share-public/docs/World of Warcraft/procedural-dungeon/` for the full design
doc.

## Layout

| Path | Contents |
|------|----------|
| `src/generator/` | **Engine-free** deterministic generator (types, RNG, pipeline, grid A*). Compiles standalone — keep it free of any engine include. |
| `src/` | Engine glue: `PDMgr` (config/pending seeds), `PDPaletteMgr` (SQL tile set), `PDWorldBuilder` (layout → spawn plans), `PDInstanceScript` (run lifecycle), `PDCreatureAI` (leash/A*-waypoints/LoS-gated casters), entrance NPC, exit/shrine GOs, `.pdungeon` commands |
| `tests/ascii_harness.cpp` | Standalone verification of the **v1 tile** generator: `g++ -std=c++17 -Wall -Wextra -Werror -O2 -Isrc tests/ascii_harness.cpp src/generator/*.cpp -o pdgen`; `pdgen <seed>` / `pdgen --batch 500` |
| `src/generator/PDBlockPlan.*` | **PDv2 block planner**: decides which kit block sits at which block coordinate and emits the `FLPD2` manifest the client composes from. Engine-free like the rest of `src/generator/`. Rooms are single blocks (66.67 yd), so the graph work is simpler than v1's rectangle packing |
| `src/generator/PDv2GameMath.h` | **PDv2 gameplay math**: the 01 §8 formulas (rooms/boss/creature-type counts, the difficulty band on its 0.25 grid, caster ratio, loot multiplier, the dxp curve). Header-only and engine-free, so the harness pins every player-visible number. Difficulty and lootMult are integers scaled by 100 end to end; `PD_GAME_ROOMS_CAP_MEASURED` is a MEASUREMENT (`pdblock --roomcap`), not a design constant, and the batch re-measures it |
| `src/generator/PDv2WalkGrid.*` + `PDv2WorldMath.h` | **PDv2 walkable surface**: walk grid built from the kit's masks, A*, path simplification, the `PlanApproach` chase policy the creature AI runs on, and the world↔block/cell math in both directions (map 760 has no mmaps — this grid IS the navigation) |
| `src/PDv2*.{h,cpp}` + `src/PDClientLink.*` | **PDv2 engine glue**: `PDv2Mgr` (config, plans, manifest, chunk-meta walk masks, per-account dlvl/dxp + cfg_* state), `PDv2PackMgr` (the two pack tables + the deterministic spawn draw; startup-loaded and read-only after, like the walk masks), `PDv2InstanceScript` (pack spawns + per-mob `PDv2MobData` tag, run lifecycle and payout, fall catcher, per-instance walk grid), `PDv2CreatureAI` (grid chase / MovePoint chains + the caster hold-at-range branch and the module's own proximity aggro — the shared templates are near-blind and must not be edited; deliberately NO leash — dungeon mobs chase until the target is gone) + the `AllCreatureScript::GetCreatureAI` binder that attaches it to stock templates on the v2 map, `PDv2Scaling` (the 01 §8 levers in one file: level-80 normalisation, difficulty on HP and outgoing damage, lootMult on gold), `PDv2MapScript`, `PDClientLink` (manifest push over the addon channel + the `OnPlayerCanEnterMap` entry gate — **crash protection**: entering with nothing composed kills the client), `PDv2UILink` (the gen panel + run HUD protocol, the 1 Hz run push, and the shared `PDv2DoGenerate`/`PDv2DoEnter` actions the `.pdungeon v2` commands and the panel buttons BOTH call), `.pdungeon v2` commands |
| `lua_scripts/flprocdungeon.lua` | The FLProcDungeon client addon, AIO-delivered (one file serves both sides). A dumb relay by design — ALL protocol logic is C++ (`PDClientLink`); deploy locally by copying to `dcore\lua_scripts\ProcDungeon\` |
| `lua_scripts/flpdui.lua` | The FLPDUI client addon (gen panel + run HUD), AIO-delivered beside the relay and deployed the same way. **Display only**: every bound, grid step and multiplier arrives from `PDv2UILink` in the `C` payload — no formula, no clamp and no `or <number>` fallback may live in this file, and a missing value renders `...` rather than a guess |
| `tests/blockplan_harness.cpp` | Standalone verification of the block planner + walk grid + approach policy + world math + client-link state machine: `g++ -std=c++17 -Wall -Wextra -Werror -O2 -Isrc tests/blockplan_harness.cpp src/generator/PDBlockPlan.cpp src/generator/PDv2WalkGrid.cpp src/generator/PDv2LinkState.cpp -o pdblock`; `pdblock <seed> [rooms]` / `pdblock --batch 500 [rooms]` / `pdblock --path <seed> [rooms]` / `pdblock --manifest <seed> <file> [rooms]` |
| `data/sql/db-world/` | `instance_template` + `map_dbc` override (base map), GO/creature templates (910000+/910500+), `pdungeon_palette`; PDv2: `mod_pdungeon_map760.sql` (generated by workspace script 47) + `mod_pdungeon_chunk_meta.sql` (generated by script 48 — **regenerate, never hand-edit**) + `mod_pdungeon_packs.sql` (creature packs; **references** fl-underground's shared creature_template entries and ships no row of its own) + `mod_pdungeon_flmats.sql` (FL mats 920100-920104) |
| `data/sql/db-characters/` | `pdungeon_runs` history; `pdungeon_account` (PDv2 persistence — layout as seed + generation inputs, regenerated on login; the three writers — layout, `cfg_*`, `dlvl`/`dxp` — update strictly disjoint column sets via ON DUPLICATE KEY, so none can clobber another); `mod_pdungeon_runs_gameplay.sql` adds the 01 §7 run columns as a **new** file, because the updater applies each file once and editing the base file would skip existing databases; `mod_pdungeon_account_bandheal.sql` is a one-time heal of `cfg_mob_level_min` (the column default of 1 selects no pack against v1's level-80 stock) |

## Core touchpoints (no core edits)

- `AllMapScript::OnBeforeCreateInstanceScript` → attaches `PDInstanceScript`
- `Map::SummonGameObject/SummonCreature` → batched build-out in `Update()`
- Per-instance dynamic collision tree → LoS (`CheckGameObjectLoS = 1`) + height
- `GameObject::SetGoState` → gate open/close (boss gate logic)

## Conventions

- Reserved IDs: GO 910000–910099, NPC 910500–910549 (registered in
  share-public `06-custom-ids.md`)
- Determinism: never use std `<random>` distributions in `src/generator/`
  (implementation-defined) — only `PDRandom` helpers; keep iteration orders
  fixed. Same seed must yield the same dungeon on gcc/clang/MSVC.
- Both harnesses must stay green: `pdgen --batch 500` and `pdblock --batch 500`
  = 0 failures.
- The block planner's manifest is a **contract with two other implementations**:
  `scripts/49_pd_compose_blocks.py` in the ForgottenLand2.0 workspace (the
  byte-exact oracle for the client composer) and the `FLPD2` parser in
  `fl-stream-client`. After changing `EmitManifest`, feed a real manifest
  through the oracle — `pdblock --manifest <seed> <file>` then
  `python 49_pd_compose_blocks.py --manifest <file>` — or the three will drift.
- AC code style, `-Werror`-clean; run `apps/codestyle/codestyle-cpp.py` from
  the module root before committing.
