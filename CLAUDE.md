# mod-procedural-dungeon

Procedurally generated dungeons: per-run unique layouts assembled at runtime
from existing WMO/M2 GameObjects on a client-known base map (default 37).
No client patch. See [README.md](./README.md) for install/usage and
`share-public/docs/World of Warcraft/procedural-dungeon/` for the full design
doc.

## Layout

| Path | Contents |
|------|----------|
| `src/generator/` | **Engine-free** deterministic generator (types, RNG, pipeline, grid A*). Compiles standalone — keep it free of any engine include. |
| `src/` | Engine glue: `PDMgr` (config/pending seeds), `PDPaletteMgr` (SQL tile set), `PDWorldBuilder` (layout → spawn plans), `PDInstanceScript` (run lifecycle), `PDCreatureAI` (leash/A*-waypoints/LoS-gated casters), entrance NPC, exit/shrine GOs, `.pdungeon` commands |
| `tests/ascii_harness.cpp` | Standalone verification of the **v1 tile** generator: `g++ -std=c++17 -Wall -Wextra -Werror -O2 -Isrc tests/ascii_harness.cpp src/generator/*.cpp -o pdgen`; `pdgen <seed>` / `pdgen --batch 500` |
| `src/generator/PDBlockPlan.*` | **PDv2 block planner**: decides which kit block sits at which block coordinate and emits the `FLPD2` manifest the client composes from. Engine-free like the rest of `src/generator/`. Rooms are single blocks (66.67 yd). **Since Round B (2026-09-02) the layout is a chain**: one path from the entrance through the boss rooms (boss *k* at `round(k·(L−1)/N)`), one-room pockets hanging off ordinary spine rooms, then the Phase-2 chest stubs; `chainIndex` / `branchOf` / `detourOf` on `PlacedBlock` are what B1/B3/B4 read (`detourOf` marks a **loop room**: since B0b an extra room beside a straight corridor run of the spine, entered from the run and left back into it two cells on — `V2.DetourChance`, 33 % per boss segment, additional to the room count). Since **B2** the role table has a **third Room alt**: `AltCountFor(Room)` is 3, so the ordinary room draws the 50 yd standard look, the blob outline or the new **33.33 yd platform** (alt 2, chunk ids `4xxx` theme 1 / `14xxx` theme 2), while the entrance and boss roles lost their 2×2 centre pad — a boss room is now an open 50×50 arena with its boss anchor in the centre. The table mirrors `ALT_COUNT` in the workspace's `48_gen_t1_blockkit.py`, and the harness proves every role/mask/alt combination against the shipped chunk-meta SQL, which is what keeps the two in step. Every boss room is a cut of the block graph (validator + harness). Design: `docs/superpowers/specs/2026-09-02-pdv2-b0-spine-generator-design.md` |
| `src/generator/PDv2GameMath.h` | **PDv2 gameplay math**: the 01 §8 formulas (rooms/boss counts, caster ratio, mob level band, loot multiplier, the dxp curve) plus the difficulty dial. Header-only and engine-free, so the harness pins every player-visible number. Difficulty is a plain integer **1..100 and open from the first run** (operator directive 2026-08-08 — dlvl gates rooms and pack unlocks, never the dial); lootMult stays an integer scaled by 100 end to end and runs x1.00 at difficulty 1 to x3.00 at 100, times the caster factor; `PD_GAME_ROOMS_CAP_MEASURED` is a MEASUREMENT (`pdblock --roomcap`), not a design constant, and the batch re-measures it |
| `src/generator/PDv2WalkGrid.*` + `PDv2WorldMath.h` | **PDv2 walkable surface**: walk grid built from the kit's masks, A*, path simplification, the `PlanApproach` chase policy the creature AI runs on, and the world↔block/cell math in both directions (map 760 has no mmaps — this grid IS the navigation) |
| `src/generator/PDv2SpawnAnchors.h` | **PDv2 typed kit anchors** (Round B / B1). Header-only, engine-free decoder for the per-chunk `anchors` JSON that script 48 writes into `pdungeon_chunk_meta`: `entry`, `boss`, `chest` and the role-tagged `spawns` (`melee`/`caster`/`elite`/`patrol`). `PDv2DecorPlan`'s `DecodeAnchorList` flattens the same JSON into one clearance list and throws the KIND away; this decoder keeps it, and the kind is what the altar (entry), the loop-room chest (chest) and B2's spawn placement (boss, spawns) read. The number reader is hand-rolled on purpose: `std::strtod`'s decimal point follows the C locale, so a comma-decimal worldserver would read the entry anchor's `29.166666` as `29`. Since **B2** the file also carries the placement itself: `PlanSpawnPoints(anchors, bossRoom, roles)` answers, for one room's picks, WHERE each stands — pick 0 of a boss room on the `boss` anchor (the arena centre), every other pick on the first unused anchor whose role matches (`elite` matches anything), then on any unused anchor, then on the legacy 12 yd overflow ring around the block centre. Pure geometry in a `PDv2SpawnPoint` (the plain names `SpawnPoint` and `PlannedSpawn` are both taken by the v1 generator): no draw, no engine include, so it can never move a layout and the harness can pin it chunk by chunk. Harness rules: every room chunk publishes an entry anchor on a walkable cell, every multi-socket corridor ≥ 2 `patrol` anchors, every dead-end stub a chest, and every planned point of every room-role chunk lands on a walkable cell |
| `src/generator/PDv2AmbushPlan.*` | **PDv2 ambush plan** (Round B / B5). Engine-free: per boss segment `Chance(V2.Ambush.Chance)` — always drawn, so a segment's coin is never skipped for want of geometry; the pick after it draws only where a segment offers two or more candidates, which is the one place the geometry reaches the stream — and on a hit one corridor of that segment's spine runs (`SpineRunInto`, so never a chest stub or a loop strip) is drawn with `UniformInt`. Runs on its OWN stream, `layoutSeed ^ PD_AMBUSH_SEED_MIX`, like the decor and critter draws, so turning the chance can never move a layout an account already owns. The chance is an operator key read live from the `.conf`, never a layout input. The harness pins the plan twice — `PD_AMBUSH_PLAN_PIN` (seed 12345 at chance 100, so it states WHERE the spots land) and `PD_AMBUSH_PLAN_PIN_MID` (seed 12345, four rooms, four bosses, at chance 50: the only check in the file that runs where `Chance` draws at all) — and re-derives the candidate corridors with its own walk |
| `src/PDv2*.{h,cpp}` + `src/PDClientLink.*` | **PDv2 engine glue**: `PDv2Mgr` (config, plans, manifest, chunk-meta walk masks, per-account dlvl/dxp + cfg_* state), `PDv2PackMgr` (the two pack tables + the deterministic spawn draw; startup-loaded and read-only after, like the walk masks), `PDv2InstanceScript` (pack spawns + per-mob `PDv2MobData` tag, run lifecycle and payout, fall catcher, per-instance walk grid; since **B2** `SpawnFromPlan` no longer rings its mobs around the block centre — it hands each room's pick roles to `PlanSpawnPoints` and stands them on the kit's published spawn anchors, the boss on the boss anchor, with the walk grid vetoing any point it calls void back onto that chunk's entry anchor (one `LOG_WARN` per chunk) and `SPAWN_SPREAD_YD`'s 12 yd circle surviving only as the overflow for a chunk without anchors or for picks past the six a room publishes; the entrance room is skipped as it always was, so it holds no pack; and since **B1 the respawn altars**: `SpawnAltars` seats one beside the entry anchor of the entrance room and of every fifth spine room — never on the socket track and never on a block-edge doorway cell — plus the loop-room chest; `BindAltar` records the player's choice, `OnUnitDeath` only *records* the death because the core is still inside `Unit::Kill` there, and the 1 Hz `RespawnPending` resurrects the player at their bound altar with resurrection sickness, with the release veto in `PDClientLink` covering that one second), and since **B3–B5 the barrier, the patrol and the ambush**: `SpawnBarriers` seats GO **910059** one cell inside every boss room's entry doorway and flips the four lane cells on BOTH sides through `SetCellsWalkable`, so a closed portcullis stops the player (a type-5 GENERIC is the only measured blocker on map 760) and the walk grid stops the creatures; `EvaluateBarrier` opens it (`go->Delete()`, cells restored, instance-wide notice) once the segment's kills reach `V2.Barrier.Pct` of what the layout PLANNED for that segment's NON-boss rooms — the denominators are `_roomPlanned`/`_segmentPlanned`, never the Lil'-Bro-inflated `_roomAlive`, and a zero denominator opens immediately — with `HintBarriers` noticing each player once inside 12 yd; `SpawnPatrols` puts one melee patroller per boss segment on the corridor run into its boss room, drawn on its own seed and scaled by `V2.Patrol.HealthMult`; `SpawnAmbushPlan` spawns nothing but stores `BuildAmbushPlan`'s spots with their picks, and the own 250 ms `TickAmbushes`/`FireAmbush` disarms a spot, stuns the player with `V2.Ambush.StunSpell` and seats `V2.Ambush.Mobs` creatures around them. Patrol and ambush mobs carry `countsForRun = false` and `roomIndex = PD_ROOM_NONE`, so they move no counter and no barrier while still rolling loot), `PDv2CreatureAI` (grid chase / MovePoint chains + the caster hold-at-range branch and the module's own proximity aggro — the shared templates are near-blind and must not be edited; deliberately NO leash — dungeon mobs chase until the target is gone; since **B4** an `isPatrol` branch in the out-of-combat path, where `UpdatePatrol` plans ONE A* beat to the tagged goal cell and `MovementInform` reverses it at the end instead of stopping the run, and the `EnterEvadeMode` override, `JustReachedHome` and the stale-run guard all REJOIN that existing beat at the nearest waypoint reachable in a straight line rather than re-planning it — without that, an evade is the normal end of a patroller's fight and the lane would shrink to wherever it was pulled) + the `AllCreatureScript::GetCreatureAI` binder that attaches it to stock templates on the v2 map, `PDv2Scaling` (the 01 §8 levers in one file: level-80 normalisation, difficulty on HP and outgoing damage, lootMult on gold), `PDv2MapScript`, `PDClientLink` (manifest push over the addon channel + the `OnPlayerCanEnterMap` entry gate — **crash protection**: entering with nothing composed kills the client), `PDv2UILink` (the gen panel + run HUD protocol, the 1 Hz run push, and the shared `PDv2DoGenerate`/`PDv2DoEnter` actions the `.pdungeon v2` commands and the panel buttons BOTH call), `.pdungeon v2` commands |
| `src/PDv2Altar.cpp` | **The altar click** (Round B / B1): a `GameObjectScript` on GO **910058**, the only file the altar owns. `OnGossipHello` carries the click to `PDv2InstanceScript::BindAltar` and returns true — every piece of state (which altar, which player, the pending-respawn map) lives on the instance script, and the altar never despawns on use, so it can be re-bound by anyone at any time. Registered from `AddPDv2AltarScripts()` in the loader |

## Core touchpoints (no core edits)

- `AllMapScript::OnBeforeCreateInstanceScript` → attaches `PDInstanceScript`
- `Map::SummonGameObject/SummonCreature` → batched build-out in `Update()`
- Per-instance dynamic collision tree → LoS (`CheckGameObjectLoS = 1`) + height
- `GameObject::SetGoState` → gate open/close (boss gate logic)

## Conventions

- Reserved IDs: GO 910000–910099, NPC 910500–910549 (registered in
  share-public `06-custom-ids.md`)
- Determinism: never use std `<random>` distributions in `src/generator/`
  (implementation-defined) — only `PDRandom` helpers; keep iteration orders
  fixed. Same seed must yield the same dungeon on gcc/clang/MSVC.
- Both harnesses must stay green: `pdgen --batch 500` and `pdblock --batch 500`
  = 0 failures.
- The block planner's manifest is a **contract with two other implementations**:
  `scripts/49_pd_compose_blocks.py` in the ForgottenLand2.0 workspace (the
  byte-exact oracle for the client composer) and the `FLPD2` parser in
  `fl-stream-client`. After changing `EmitManifest`, feed a real manifest
  through the oracle — `pdblock --manifest <seed> <file>` then
  `python 49_pd_compose_blocks.py --manifest <file>` — or the three will drift.
- AC code style, `-Werror`-clean; run `apps/codestyle/codestyle-cpp.py` from
  the module root before committing.
